# Сборка npm-пакета данных

## Подготовка инкрементальной доставки

Та же команда `npm run data:prepare -- --config /path/to/config.json` умеет
подготовить полный npm-пакет и инкрементальную доставку. В конфигурации добавьте:

```json
{
  "incremental": {
    "packUrl": "https://github.com/OWNER/REPO/releases/download/apollo-data-{version}/objects.bin"
  }
}
```

`packUrl` — HTTPS-ссылка на зашифрованный файл объектов с поддержкой HTTP Range.
`{version}` заменяется текущей версией пакета, как и в `tarballUrl`.
Proxy запрашивает только диапазоны отсутствующих или изменившихся файлов,
проверяет ответ 206, точный диапазон, SHA и аутентификацию каждого объекта.
Ответ 200 не приводит к скачиванию всего файла: обновление безопасно отказывается.
Для хоста отдельных объектов вместо `packUrl` можно указать `objectsUrl` —
постоянный HTTPS-каталог. Эти режимы взаимоисключающие.
Сборка никуда не загружает данные. Подготовленная
ссылка inventory выводится из `tarballUrl`: рядом с tgz располагается
`incremental.json.enc`. Выход версии содержит этот файл, `objects.bin` для Range,
локальные `objects/*.enc` для переиспользования следующей сборкой, полный
tgz, кандидат `current.json` v4 и отчёт. Содержимое и список файлов знаний
зашифрованы; ключ в эти артефакты не записывается.

Если предыдущий результат этого output существует, сборщик переиспользует его
шифрованные объекты. Можно явно задать `incremental.previousRoot` — каталог
предыдущей подготовленной версии с `current.json`, `incremental.json.enc` и
`objects/`. Относительный путь считается от файла конфигурации. Новый output
самодостаточен: содержит все объекты, на которые ссылается его inventory.
В режиме Range публикуются `objects.bin`, inventory и полный tgz. Локальный
каталог `objects/` публиковать не нужно. В режиме отдельных объектов можно не
загружать уже существующие неизменяемые объекты.

Проверка подготовки проходит через реальный incremental consumer от базового
release в удаляемом store. Кэш `UNCHANGED` проверяет также хэши inventory и всех
объектов. Без `incremental` сохраняются прежние v3-сборка и полный consumer.

Публикация остаётся отдельным действием: сначала все объекты и inventory должны
быть доступны по подготовленным URL, затем переключается только канал
совместимого нового Proxy. Не заменяйте v3-канал старых установок индексом v4.
Локальная подготовка не обновляет установленное приложение или его данные.

`data:prepare` — одна локальная команда для сборки Apollo runtime, знаний и
защищённого npm-пакета. Агент и Figma в процессе не участвуют. Она использует
существующие сборщики и проверяет результат штатным загрузчиком.
Установленные приложение и Proxy, Git-канал и публикация не меняются.

## Один раз настроить входы

Создайте личный JSON вне Git. Все пути разрешаются относительно этого файла;
папки `workplace` и установленного приложения не требуются.

```json
{
  "schemaVersion": "apollo.data-package-build.v1",
  "baseRelease": "./accepted/seed",
  "baseRuntimeRoot": "./accepted/runtime",
  "apolloRoot": "../apollo",
  "designSystemRoot": "../design-system_ab",
  "dsAiHubRoot": "../ds-ai-hub",
  "activationFile": "./publisher/activation.json",
  "outputRoot": "./prepared",
  "tarballUrl": "https://github.com/OWNER/REPO/releases/download/DATA_TAG/apollo-data-{version}.tgz",
  "passwordCommand": ["swift", "/path/to/apollo-proxy/macos-app/scripts/data-publisher.swift", "password"]
}
```

`baseRelease` — принятый полный снимок данных с `manifest.json`, `contracts`,
`knowledge` и, если объявлены, `skills`. Он может быть извлечён из прежнего
принятого артефакта; работающий Proxy для этого не нужен.
`baseRuntimeRoot` — совместимый runtime для проверки старого снимка.
`apolloRoot`, `designSystemRoot`, `dsAiHubRoot` — собственные Git checkout.
Зависимости Apollo и Proxy устанавливаются один раз через `npm ci` в каждом
из двух репозиториев; Git, Node/npm и прежний secret store должны быть доступны.
В обычном случае generation skills берутся из `apolloRoot/skills`; отдельный
принятый источник можно указать в `generationSkillsRoot`.

Команда запускает существующий `npm run build` внутри `apolloRoot`. Он обновляет
локальные `dist` Apollo и его пакетов: этот checkout должен иметь одного writer,
без параллельной сборки или зависящего от него прогона. Установленный плагин от
этого не обновляется. Изменение исходников во время сборки останавливает выдачу
пакета. Режимы native diagnostics и специального native scope для этой обычной
сборки не используются; при их наличии в окружении команда явно отказывает.

Если runtime изменился относительно baseline, отчёт укажет `runtimeChanged: true`: перед доставкой
данных потребуется совместимое обновление приложения/runtime. Собранный runtime
сохраняется рядом с npm-архивом, но установленное приложение не подменяется.

`activationFile` содержит публичные параметры **существующей** активации.
Отсутствующий файл вызывает ошибку; новый ключ не создаётся. Команда
`passwordCommand` получает пароль из существующего Keychain издателя, передаёт
его внутри процесса и не помещает в argv, environment, отчёт или файл. Не
записывайте пароль литералом в эту команду. Без `passwordCommand` утилита читает
JSON `{"password":"…"}` из приватного stdin; это поддерживает CI/другой secret
store. Не помещайте пароль в shell history.

## Повседневная команда

```bash
npm run data:prepare -- --config /path/to/private-build.json --version 1.4.3-data.20261028.1
```

Утилита:

1. Собирает Apollo из исходников через `npm run build` и готовит переносимый runtime.
2. Собирает знания из `design-system_ab` и `ds-ai-hub` существующим knowledge
   producer. Точные Git refs и fingerprint исходников записываются в отчёт.
3. Проверяет baseline, runtime, canonical index, manual/facts и закреплённые ZIP.
   Выбирает прежний состав по `contractId`; сопоставляет platform/component
   identity, обновляет изменившиеся контракты через существующий importer.
   Остальные записи, зависимости и mapping сохраняются. Устаревший mapping
   отклоняется штатным reader, автоматически не переписывается.
4. Собирает full release: контракты, новые знания и правила навыков. Skills данных
   сохраняются из baseline, если не задан другой принятый `skillsRoot`.
   Authoring норм/фактов и проверка макетов остаются отдельной работой.
5. Шифрует данные прежним ключом, запускает настоящий `npm pack --ignore-scripts`
   и загружает архив штатным protected consumer в удаляемый временный store.
6. Оставляет `.tgz`, каталог `runtime`, кандидат `current.json` и `report.json`
   в папке `outputRoot/<version>`. Временные открытые знания, store проверки
   и дубли шифрованных файлов удаляются, в том числе при ошибке.

Повтор с теми же входами возвращает `UNCHANGED`, прежнюю версию и прежние байты;
пароль не запрашивается, новый npm-архив не создаётся. Компиляция Apollo и
проекция знаний выполняются, чтобы не упаковать устаревший `dist`.
Для изменённых данных нужна новая явная npm-версия. Одновременные сборки в одном
output блокируются lock-файлами. Не удаляйте lock, пока сборщик работает.

В отчёте доступны contentVersion, runtimeId, обновлённые контракты и `excluded` —
позиции canonical index, ещё не входящие в baseline. Новые компоненты не
подключаются молча. Фиксированного лимита «36 контрактов» нет.
Текущий reader не поддерживает два контракта с одинаковым componentId, поэтому
desktop и mobile ButtonsGroup пока нельзя включать одновременно. BenefitsBlock
и PromoCard также не входят в текущую поставку; причина их прежнего исключения
не установлена. Добавление в поставку требует отдельного изменения состава.

Данные frontend/SDK в профиль `checking-ask-figma-mcp` не включаются.
arui-private не читается и не упаковывается.

## Упаковка уже готовых входов

Прежний режим сохранён: опустите `apolloRoot` и `dsAiHubRoot`, задайте
`runtimeRoot` и при необходимости `knowledgeRoot`. Тогда source build не
запускается: runtime и знания берутся из готовых принятых каталогов, по умолчанию
knowledge — из baseline. `baseRuntimeRoot` нужен, если старый снимок требует
другого runtime. Можно опустить и `designSystemRoot`, чтобы переупаковать
принятый снимок без обновления контрактов. Команда остаётся той же.

## После сборки

Проверенный кандидат ещё не опубликован. Публикуйте точный зашифрованный `.tgz`
отдельным действием, проверьте доступность и затем обновите соответствующий
совместимому runtime Git-индекс. Локальный `current.json` — кандидат, а
`last-build.json` — служебный кэш утилиты; не подменяйте ими рабочий канал
автоматически. Если серверное имя asset отличается от указанного в config,
исправьте config до сборки. Номер npm-пакета, версия данных и версия приложения
имеют разные назначения; сборка пакета данных не выпускает приложение.

При смене runtime публичный миниапп остаётся пустым, а новый пакет публикуется
по отдельному runtime-каналу. Сначала становятся доступны зашифрованный архив
и совместимый индекс, затем выпускается миниапп через Sparkle. Прежний канал
сохраняется для старых клиентов.

Миниапп переносит только прежние штатные адреса на канал своей новой сборки;
пользовательские URL сохраняются. При обнаружении целого пакета другого runtime
он не используется для запуска. Существующий доступ из Keychain позволяет
загрузить совместимые данные при запуске прокси без повторного ввода пароля.
После проверки новый пакет атомарно становится текущим, прежний остаётся для
отката. Повреждённый пакет не считается обычной миграцией; ошибка загрузки
сохраняет исходное хранилище и останавливает автоматический повтор запуска.

Для чистой упаковки миниаппа `build-app.sh` принимает `APOLLO_PROXY_SOURCE_ROOT`
с экспортом выбранного Git-коммита Proxy. Swift собирается в исходном checkout
с его кэшем, а код для встраивания берётся из этого экспорта. Не подключайте
весь `.build` через симлинк к другому package path: пути Clang-модулей конфликтуют.

## Существующие raw-каталоги пилота TitleView

При `designSystemRoot` сборщик берёт существующие `catalog-source.json` и
`dependency-sources.json`, закрепляет raw SHA и регистрирует TitleView с 11
зависимостями в `rawCatalogs` даже без изменения manual/compiled контрактов.
Новый native-блок и отдельные файлы снимков не требуются. Выбранное дерево
собирается прежним V3 `resolveStructure`; `catalog-resolve` также возвращает
карту опубликованных ключей вариантов к семействам и pins исходных каталогов.
Неоднозначный ключ исключается из карты с явной причиной, не выбирается первый.
Изменение descriptor или raw инвалидирует прежний input snapshot.
Эта локальная подготовка не обновляет публичный канал или установленный Proxy.

## Подготовка полного набора для проверки V3

Для нового runtime с capability `auditDataPreparation: apollo.v3-audit-data.v1`
применяется следующий режим вместо обновления manual/facts/ZIP из шага 3 выше:

- `data:prepare` использует чистый bundle `dist/v3-audit-preparation.cjs`, собранный
  обычным build Apollo и закреплённый в portable runtime. Он переиспользует
  существующие V3 readers/normalizers; пакет знаний не содержит исполняемый код.
- В `designSystemAbmRoot` можно явно указать собственный checkout
  `desing-system_abm`. По умолчанию это сосед `designSystemRoot` с таким именем.
  Он нужен producer наравне с `design-system_ab` и Hub, но установленному Proxy
  эти checkout не нужны. Отсутствующие файлы не скачиваются автоматически.
- Builder проходит main/ABM reference manifests, каталоги и индексы, стили/токены,
  старые V3 политики и redpol JSON. Сырые Athena `structure`/`variantStructures`
  сохраняются без compact-проекции. Семь старых артефактов семейства и нормализация
  V3 не заменяются V4 manual/compiled/predicate engine.
- Native-проекция хранится отдельно в `data/v3-audit`. Каждый gzip JSON-конверт
  имеет storage SHA/размер, исходный SHA/размер и opaque ID в manifest. Нет
  дополнительного лимита 64 MiB на допустимый исходный каталог; reader
  ограничивает декодирование точной заявленной исходной длиной. Все raw pins
  повторно сверяются перед выдачей результата.
- Прежний baseline `contracts` сохраняется для существующих модулей без
  перекомпиляции manual-контрактов. Их отсутствие в authoring checkout не блокирует
  новый режим. Обычная knowledge-проекция и Skills также сохраняются.

Для отдельной локальной подготовки знаний существующий
`build-knowledge-package.js` принимает `--audit-runtime-root /path/to/accepted-runtime`
и `--audit-abm-root /path/to/desing-system_abm`; остальные параметры прежние.
Без первого параметра поддерживается прежняя проекция для совместимых старых
поставок, но она не считается готовыми данными V3. Новому runtime отсутствие
V3-набора даёт `DATA_PREPARE_AUDIT_DATA_REQUIRED`; новому набору со старым кодом —
`DATA_PREPARE_AUDIT_CODE_REQUIRED`. Эти ошибки не включают старый пилот проверки.

Декодер проверяет внешнюю knowledge-поставку и только нужный актив, не распаковывая
всё на каждый запрос. При смене dataId, изменении файла, неправильном gzip или
SHA запрос прекращается; Git/HTTP fallback отсутствует. История, установленный
код и публичный канал этой подготовкой не меняются. Установка и Figma-тесты
по-прежнему выполняются владельцем после совместимого выпуска.
