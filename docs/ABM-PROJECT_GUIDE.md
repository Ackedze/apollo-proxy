# Требования к выдаче ответов АБМ

Согласованные требования и существовавший черновик формата восстановлены
из состояния до настройки отдельного dev-Proxy.
Текст инструкции и сборка запроса находятся в
[ABM-messages.js](../src/reports/ABM-messages.js).

Инструкция подключена к существующему маршруту «Спросить» Codex/Claude
для вопросов с явным «АБМ» / «ABM». Последующий вопрос наследует последнее
явное указание библиотеки из пользовательских сообщений; указание «АБ»
возвращает прежний путь. Сообщения ассистента библиотеку не переключают.
Без указания АБМ сохраняются прежний промпт и источник АБ.
Переключатель iOS/Android текущего плагина в этот запрос не передаётся.

Для проверки используется временный запуск текущего checkout по инструкции
разработки, с отдельным состоянием и совместимыми runtime/данными.
CODEX_ABM_PATTERNS задаётся только в окружении этого процесса и указывает
на предоставленную папку patterns. Настройки установленного приложения
не изменяются. Дополнительного checkout и .command-файла нет.

Перед тестом завершите свой обычный Apollo Proxy после окончания активного
запроса. Временный процесс занимает localhost:3001, куда обращается существующий
плагин Apollo. Начните новый чат и явно укажите АБМ в первом вопросе.
После теста остановите временный процесс и вернитесь к обычному Apollo Proxy.
Изменения остаются в рабочей ветке и не публикуются.

Источники АБМ проверяются по abmDocumentType: Pattern и abmPatternID.
В установленном ds-ai-hub сейчас лежат преобразованные документы без этих
полей, поэтому исходные MD не подменяются файлами Hub. При недоступности
или изменении MD-файлов во время запроса ответ явно отклоняется.
В knowledgeRelease ответ АБМ обозначен abm-local-<fingerprint>,
без приписывания ему commit-метаданных другой базы.

Ответы строятся только по трём закрытым шаблонам. При отсутствии
однозначного подтверждения используется утверждённая фраза; автоматическое
уведомление команде не отправляется.

## Подтверждённое требование 1: поиск по метаданным

Сначала просматривать frontmatter паттернов, чтобы выбрать кандидатов
без предварительного чтения полного текста каждого документа.

| Поле | Использование |
| --- | --- |
| abmDocumentType | Определить тип документа Pattern |
| abmPatternID | Точный поиск по переданному идентификатору |
| abmPatternTitle, tags | Найти тему вопроса |
| abmPatternType | Уточнить категорию паттерна |
| platform | Выбрать применимую платформу |
| version, updatedAt | Сохранить версию и дату источника |
| editor | Сохранить сведения о редакторе |

После выбора кандидатов читать нужные разделы. Метаданные не заменяют
содержимое правила. Если кандидатов нет, расширить поиск на заголовки и текст.
Это инструкция поиска для агента; отдельный индекс и измерение ускорения
в рамках этого требования не реализованы.

## Подтверждённое требование 2: правила, подправила и примеры

- Читать [Rule] вместе с условиями, исключениями и контекстом раздела.
  Подправила R02.1 и R02.2 читать с общим родительским R02.
- Сначала искать собственный [RuleExample] с тем же ключом, например
  R06_ungrouped_four_digit_numbers_in_text.
- Если собственного примера нет, использовать общий [RuleExample] родителя:
  пример R02 подходит к R02.1 и R02.2 при выводе любого из них.
  Не брать пример соседнего подправила; учитывать структуру внутри того же паттерна.
- При наличии связанного примера всегда выводить доступные ссылки из Markdown:
  отдельно iOS и отдельно Android. Не ограничивать ссылки одной платформой молча.
- Общий пример можно дать один раз внутри ответа на один вопрос.
  Для разных вопросов нужные примеры повторяются под каждым ответом.
- Если пример есть только для одной платформы, показывать только фактическую ссылку.
- Если нет собственного или общего родительского примера, ссылку не давать.
  Используется фраза «Правило есть, но примера к нему не нашёл.».
- Общая ссылка figma_url и ссылка раздела не заменяют отсутствующий пример.

Это инструкция чтения и выдачи для агента. Отдельный детерминированный парсер
связей [Rule]/[RuleExample] на этом шаге не добавляется.

## Подтверждённое требование 3: общая база и внимание человека

Единственный источник ответа — правила в предоставленных MD-паттернах АБМ.
Фильтр после уточнения пользователя: **abmDocumentType: Pattern**,
как в текущих файлах; documentType: abmPattern не используется.
Метаданные помогают найти документ, примеры иллюстрируют правило.
Знания модели, история и гайды не восполняют отсутствующие нормы.
Паттерны приоритетны и при будущем добавлении гайдов платформ.

| Ситуация | Видимый блок ответа дизайнеру |
| --- | --- |
| Правило не найдено | Утверждённая короткая фраза с названием чата, без заголовка и подробностей |
| Правила противоречат | Утверждённая фраза отсутствия однозначного ответа |
| Информация есть в нескольких паттернах | Только точные выдержки в шаблоне; если нужна интерпретация, фраза отсутствия ответа |

Перед фиксацией противоречия сопоставлять платформы, условия и исключения.
Не выбирать победителя самостоятельно. При конфликте использовать
утверждённую фразу отсутствия однозначного ответа. Несколько источников
не разрешают добавлять свободные выводы и предупреждения.

### Сигнал команде — требование к следующему этапу

Зафиксирована потребность сообщать команде о пробелах, противоречиях
и информации, распределённой по нескольким паттернам. Канал получения,
получатели, состав данных, хранение и устранение повторов пока не выбраны.
Возможные категории сигнала для обсуждения: отсутствие правила,
конфликт правил, несколько источников. Их названия и формат API не утверждены.

Последнее требование о закрытых шаблонах отменяет свободные предупреждения
и дополнительные блоки в ответе дизайнеру.
Автоматическое уведомление, структурированные события, задачи и визуальные
элементы UI не реализованы. Ответ не должен утверждать, что сигнал команде
отправлен. Фактическое соблюдение блоков моделью требует проверки на примерах.

## Подтверждённое требование 4: оформление источника

Ответ → Пример iOS · Пример Android → Паттерн: «Название», v.X.X.

Версию брать из источника. Даты, разделы, ID правил и метку «Источник»
не показывать. Примеры — реальные Markdown-ссылки. Если есть пример только
одной платформы, показывать его. Если примеров нет, использовать фразу ниже.

## Подтверждённое требование 5: строго на вопрос

Не отвечать на похожую тему по совпадению слов и не предполагать сценарий.
Если контекста недостаточно для точного однозначного ответа, использовать
утверждённую фразу отсутствия ответа. Уточняющие вопросы запрещены.
Не выдавать частное правило за общий ответ. Не добавлять непрошеные темы
и сообщения об отсутствии ответа на вопросы, которые пользователь не задавал.

## Подтверждённое требование 6: несколько вопросов

Никаких таблиц и списков, в том числе при сравнении. Ответы — обычными абзацами.
Если вопросов несколько, повторять каждый вопрос отдельным абзацем,
далее его ответ, примеры и подпись паттерна с версией. Сохранять порядок вопросов.
Не собирать примеры общим списком в конце. У каждого вопроса должны быть
свои связанные примеры; общий пример при необходимости повторять.

## Подтверждённое требование 7: утверждённые фразы

Если точного ответа после успешного поиска нет:

> Не нашёл ответа в паттернах АБМ. Напиши в чат «DS ABM :: Скорая помощь по дизайну» — мы ответим на твой вопрос

Без заголовка «Нет ответа в паттернах», подробного объяснения, похожего ответа,
несвязанных примеров или подписи не ответившего на вопрос паттерна.
Неоднозначность вопроса также приводит к этой фразе. Техническая ошибка
транспорта или чтения обрабатывается сервисом отдельно.

Если ответ есть, но пример отсутствует:

> Правило есть, но примера к нему не нашёл.

Фраза занимает место ссылок после ответа и перед подписью паттерна.
URL чата не предоставлен: название остаётся обычным текстом.

## Подтверждённое требование 8: дружелюбный тон

Обращение на «ты». О результате поиска говорить от первого лица.
Не принуждать каждый ответ начинаться с «я нашёл». Не добавлять канцелярит,
лишние подробности поиска и шаблонные предложения продолжить.
Все прежние требования к достоверности и условиям правил сохраняются.

Техническая подпись под сообщением рисуется плагином Apollo отдельно
от ответа модели. Изменение или удаление этой подписи в этот пакет не входит.


## Подтверждённое требование 9: три закрытых шаблона

Последнее требование имеет приоритет над прежним разрешением уточнений
и свободных формулировок. Модель возвращает JSON по ABM_RESPONSE_SCHEMA:
вопрос, статус answer/not_found, файл, ключ правила и точную выдержку.
Дизайнер JSON не видит.

ABM-response.js строит Markdown кодом. Название и версия берутся из MD,
версия — только из version. Номер раздела или ID не может заменить версию.
Примеры выбираются по собственному RuleExample либо общему родительскому.
Если факты не подтверждены, контекст неясен или требуется интерпретация,
используется только утверждённая фраза отсутствия ответа.
Уточняющие вопросы, похожие случаи и собственные рекомендации запрещены.

Выдержка должна дословно присутствовать в тексте выбранного правила.
Код проверяет это с нормализацией пробелов и не выводит неподтверждённый текст.
Модель продолжает выполнять поиск и выбор релевантного правила; эта проверка
не доказывает семантическую полноту выбора, но исключает свободную генерацию
версии, ссылок и формата подписи.

Для нескольких вопросов каждый блок имеет один из трёх шаблонов.
Ошибки самого транспорта/чтения остаются ошибками сервиса, а не утверждением
об отсутствии правила. Установленный Apollo Proxy и ветка main не меняются.

Явный выбор библиотеки сохраняется на время процесса по session_id
(до 256 последних сессий), даже когда первое сообщение вышло за лимит истории.
Явное указание АБ переключает обычный путь; новый чат создаёт новую сессию.
