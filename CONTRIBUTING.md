# Разработка Apollo Proxy

Работа над «Спросить» ведётся в своей ветке и локальной сборке. Владелец проекта
@Ackedze выполняет окончательное ревью и публикацию. Доступ к исходникам не даёт
права менять рабочие данные, чужую авторизацию или опубликованный релиз.

Дизайнеру начать с [общей инструкции старта](https://github.com/Ackedze/apollo/blob/main/docs/DESIGNER_START.md):
доступы, установка, данные, локальная разработка и поручение своему агенту.

Основная инструкция агенту-разработчику находится в репозитории Apollo:
[`docs/AGENT_START_ASK.md`](https://github.com/Ackedze/apollo/blob/main/docs/AGENT_START_ASK.md).
Установка готового приложения описана отдельно в
[`macos-app/DELEGATION.md`](macos-app/DELEGATION.md).

## Задача, ветки и доступ

- Зафиксируйте результат и границы в Issue или существующем поручении владельца.
  Уже выданное поручение не требует повторного согласования. Небольшая правка
  документации не требует отдельного Issue.
- Владелец и агенты по его прямому поручению работают в `main`. Внешние участники
  и их агенты создают свои ветки от актуального `main`, тестируют локально и
  открывают PR в `main`. Если выдан другой ref поставки, укажите его явно.
- Доступа `Write` достаточно для своих веток; без него используйте fork и PR
  в исходный репозиторий. Права `Admin` и публикационные секреты не нужны.
- Не делайте self-merge, force push, не меняйте защиту веток и чужую установку.
  Итоговое решение и merge — у **@Ackedze**, выпуск выполняется отдельно.
- Используйте собственный checkout, зависимости, конфигурацию и `dist` Apollo.
  Общие source/build меняет один writer; не пересобирайте используемые коллегой
  входы во время его проверки. Изолированная папка вывода не изолирует чтение source.

Из новой рабочей папки с доступом на запись:

```bash
git clone https://github.com/Ackedze/apollo.git projects/Apollo
git clone https://github.com/Ackedze/apollo-proxy.git services/apollo-proxy
git -C services/apollo-proxy switch -c contributor/ask-links
```

Выберите своё имя ветки; если меняется Apollo, создайте ветку и в нём.
Для fork замените URL нужного репозитория и добавьте оригинал как `upstream`.

## Изолированная проверка чата

Требуются Node.js 22 и npm. Из произвольной папки checkout Proxy:

```bash
npm ci
node --test test/dialogue-source.test.js test/dialogue-runtime.test.js test/cli-agent.test.js
```

Тесты создают собственные knowledge/CLI fixtures. Им не нужны личный вход,
workspace автора, Figma MCP или `arui-private`. CI `Ask regressions` выполняет
именно этот ограниченный набор; он не подменяет полный интеграционный прогон.

## Полная проверка

`npm test` по-прежнему проверяет весь Proxy, включая проверки реальных каталогов
и совместимость с Apollo. Ему нужны принятые исходники Apollo, данные
`design-system_ab` и знания `ds-ai-hub`. Передавайте их через настроенные корни
и зафиксированные версии. Не копируйте личный `.env` автора и не скачивайте
произвольный новый каталог ради прохождения теста.

Для текущих cross-repository тестов используйте структуру внутри любой своей
папки: `projects/Apollo`, `services/apollo-proxy`, `shared/design-system_ab`.
Путь к knowledge `ds-ai-hub` задаётся `DS_AI_HUB_ROOT`; для запущенного сервера
корни знаний задаются `CODEX_DESIGN_SYSTEM` и `CODEX_DS_AI_HUB`. Эти имена
окружения для тестов и сервера различаются. Полный набор входов и проверки
смотрите в инструкции Apollo. На macOS используйте `TMPDIR=/private/tmp`.

Если интеграционные данные ещё не выданы, выполните доступные проверки чата
и явно укажите, что полный прогон не выполнен. Не меняйте guards, expected
values или skip ради отсутствующих входов. До merge затронутую интеграцию
проверяет maintainer на принятом наборе.

## Pull request и выпуск

Один PR решает одну задачу. Исправление поведения сопровождается regression-тестом,
новая функция — проверками основного сценария и существенных ошибок. Используйте
существующие модули и зависимости; не добавляйте fallback, скрывающий отсутствие
контракта, знания или ошибку provider. Сохраняйте cancellation, privacy и различие
UNKNOWN/failed/passed. При изменении поведения обновите README.

Один пользовательский сценарий может потребовать два связанных PR: Apollo и
Proxy. Укажите ссылки в обоих, порядок merge и совместимость во время обновления
одной стороны. Проверяйте ошибку, пустой ответ, повтор запроса и ссылки вместе
с успешным ответом. Используйте синтетические fixtures без реальных отчётов.

В PR укажите commit обоих checkout, build/версию поставки, dataId, команды и
результаты проверок, ручные сценарии и ограничения. Раскройте использование AI:
инструмент, изменённые им части и то, что автор проверил сам. Автор отвечает за
результат и должен уметь объяснить изменение.

`CODEOWNERS` оставляет владельцем всех файлов @Ackedze. Workflow
`Required owner review` требует его approval для текущего head commit.
Защита `main` на GitHub уже включает обязательные `Ask without author workspace`
и `Required owner review`, code owner review, отклонение устаревшего approval,
актуальную базу и запрет force push/удаления ветки. После правок нужен новый
approval текущего head commit. Администратор сохраняет bypass для работы владельца
напрямую в `main`. Наличие файлов в fork само по себе не включает эту защиту.

Перед подключением участника владелец проверяет, что `CODEOWNERS` и workflows
уже находятся в **удалённом `main`**, а имена обязательных checks совпадают
с реальными jobs. Если файлы есть только локально, сначала доставить их в `main`:
до этого нельзя считать автоматическое финальное ревью настроенным полностью.

Merge в `main` и публикация — разные действия. Перед выпуском проверяется
согласованная пара версий кода и пакет данных. Секреты публикации и изменение
stable channel остаются у владельца. Не коммитьте `runtime/`, `.env`, логи,
историю, собранные приложения и приватные каталоги.

Не добавляйте зависимости от личного `workplace`, абсолютных путей, credentials
или установленного skill автора. Готовая поставка получает данные через Proxy;
собственный dev-сервер использует явно настроенные принятые корни. Аккаунты агента
и Figma MCP принадлежат участнику и настраиваются им. `arui-private` запрещено
push-ить, копировать в публичный Git, архивы или fixtures; текущий чат его не требует.
